# 실제 허밍 평가 절차 (P6-08, Phase 6 결정 9)

목적: 한 사람의 실제 허밍 20테이크 이상으로 C-09 목표(전체 F1 ≥ 0.90, 시작 허용 오차 0 tick)를 확인한다.
통과하지 못하면 녹음 기능을 "실험 기능"으로 표시한다(결정 9). 결과는 녹음한 사람·기기·환경에 대한 것이며
다른 목소리·기기의 품질을 보장하지 않는다.

## 1. 개인정보와 파일 위치

- 녹음 파일은 **저장소 밖** 폴더에 둔다(예: `~/Documents/humming-eval`). 도구는 저장소 안 폴더를 거부한다.
- 녹음은 커밋·업로드하지 않는다(Phase 4 결정 7). 도구는 폴더를 읽고 같은 폴더에 보고서 한 개만 쓴다. 네트워크를 쓰지 않는다.
- 평가가 끝나면 녹음은 지워도 된다. 저장소에는 보고서의 수치만 TASKS/TEST_PLAN에 옮겨 적는다.

## 2. 준비

```bash
mkdir -p ~/Documents/humming-eval
npm run eval:humming -- --init ~/Documents/humming-eval
```

정답 JSON 20개(`scale-1.json` … `waltz-4.json`, 5개 선율 × 4회)가 생긴다. 이미 있는 파일은 덮어쓰지 않는다.

| 선율 | 내용 | 템포(4분음표/분) | 박자 |
|---|---|---|---|
| scale | 도레미파솔라시도, 4분음표 2마디 | 90 | 4/4 |
| repeated | 솔솔솔솔 라라 솔– 파파 미미 레– 도– | 90 | 4/4 |
| rests | 도 (쉼) 미 (쉼) 솔– (쉼–) 파 미 (쉼–) 도–– | 90 | 4/4 |
| eighths | 8분음표 진행 2마디 | 80 | 4/4 |
| waltz | 미 파 솔 도'–– 시 라 솔 미–– | 110 | 3/4 |

음역은 C4(가온 도)–C5. 한 옥타브 낮게 부르는 것이 편하면 그 테이크 JSON의 `"octaveShift": 0`을 `-1`로 바꾼다
(정답 음 전체가 12반음 내려간다). 다른 값은 고치지 않는다.

## 3. 녹음

1. 조용한 방. 에어컨·선풍기는 끈다. Mac 내장 마이크 또는 휴대폰, 입에서 30–50 cm.
2. 메트로놈은 **이어폰으로** 듣는다(클릭 소리가 녹음에 들어가지 않게). 템포는 표의 값.
3. 녹음 시작 → 메트로놈 1마디를 듣고 → 다음 마디 첫 박에 첫 음을 시작한다.
4. 음마다 "따" 또는 "라"처럼 살짝 끊어 부른다(같은 음 반복을 구분하기 위해). 쉼표에서는 소리를 내지 않는다.
5. 마지막 음이 끝나면 1초쯤 조용히 있다가 녹음을 멈춘다. 테이크당 한 번에, 다시 부르면 그 파일을 새로 녹음한다.
6. 같은 선율 4회는 연달아 부르지 말고 다른 선율과 섞어 녹음한다(학습 효과 완화).

파일 이름은 JSON과 같게 한다: `scale-1.wav`. QuickTime/음성 메모가 만든 `.m4a`는 WAV로 바꾼다.

```bash
afconvert -f WAVE -d LEI16@44100 scale-1.m4a scale-1.wav
```

지원 형식: PCM 16/24/32-bit, 32-bit float, 모노 또는 스테레오(평균해 모노로).

## 4. 실행과 판정

```bash
npm run eval:humming -- ~/Documents/humming-eval
```

같은 폴더에 `humming-report-<시각>.md`가 생긴다. 판정:

- **PASS**: 채점된 테이크 ≥ 20, 전체 F1(마이크로 평균) ≥ 0.90.
- **FAIL**: 테이크는 충분하지만 F1 < 0.90 → 결정 9에 따라 녹음 기능을 "실험 기능"으로 표시하는 작업을 연다.
- **INSUFFICIENT**: 채점된 테이크가 20개 미만. 판정하지 않는다.

정답이 있는데 소리가 없거나 음을 못 찾은 테이크는 제외하지 않고 **정답 음 전체를 놓친 것**으로 센다.
짝이 없는 파일(WAV만, JSON만)은 오류 행으로 보이며 점수에 들어가지 않는다.

## 5. 시작 위치 정렬

앱의 녹음은 카운트인 클릭으로 tick 0을 알지만, 외부 녹음기에는 그 정보가 없다. 그래서 정답 JSON에
`downbeatSeconds`(WAV에서 첫 마디 첫 박의 초)가 없으면 **첫 검출 음을 첫 정답 음 위치에 맞춘다**(`first-note`).

- 장점: 녹음 시작 시점과 무관하게 음높이·분할·상대 리듬이 그대로 채점된다.
- 한계: 일정한 시작 지연은 점수에 반영되지 않는다. 첫 음 앞의 숨소리·잡음이 음으로 검출되면 테이크 전체가 밀려
  점수가 크게 떨어진다. 그런 테이크는 보고서에서 보이므로, 다시 녹음하거나 `downbeatSeconds`를 직접 적는다.

정답 JSON 형식:

```json
{
  "note": "자유 메모(선택)",
  "tempoBpm": 90,
  "timeSignature": { "numerator": 4, "denominator": 4 },
  "key": { "tonic": "C", "alter": 0, "mode": "major", "fifths": 0 },
  "octaveShift": 0,
  "downbeatSeconds": 1.333,
  "notes": [{ "midi": 60, "startTick": 0, "durationTicks": 960 }]
}
```

`key`(기본 C장조, 철자에만 쓰임)·`octaveShift`(기본 0)·`downbeatSeconds`(기본 first-note 정렬)·`note`는 선택.
tick은 4분음표 = 960.

## 6. 도구 자체 검증

`tests/unit/humming-eval.test.ts`: WAV 읽기(16/24/32-bit, float, 스테레오, 알 수 없는 청크), 정답 검증,
합성 허밍 WAV로 F1 = 1, 틀린 정답·무음·짝 없는 파일, 판정 경계, 템플릿. 합성 신호 점수는 실제 허밍 품질과 무관하다.
분석 경로는 편집기와 같은 `transcribeRecording`(음높이 추적 → 분할 → 양자화)이며 도구를 위해 Domain을 바꾸지 않았다.
